# Runs by an agent

An AI agent can run measurements on the bench, but only inside an approved plan. This chapter covers connecting an agent, approving its plan and following its runs.

## The plan

The agent proposes a plan before it runs anything. A plan states:

| Part | Content |
|---|---|
| Goal | What the agent intends to measure, and why |
| Envelope | The modules it will run; each parameter it will set, with the range it may take; the loops it will use, with their values |
| Caps | The number of runs, their total estimated time, and how long the approval lasts (at most 7 days) |

A scan counts as setting the parameter it sweeps: a V_coll scan is held to the plan's V_coll range, and a parameter the plan does not list cannot be swept. A parameter the plan does not list cannot be set by the agent: it keeps the value the operator chose on the bench, from `run.toml`, the last run or an edit (3.1).

## Automatic approval

`rig.toml` sets who approves:

| `[plans] auto_approve` | A plan is |
|---|---|
| `true` | Approved as it is proposed. Nobody clicks; the plan panel shows it as `Approved: auto_approve in rig.toml` and the journal records the same reason |
| `false` or absent | Proposed, and waits for a person in the panel |

The agent writes its own envelope, so under automatic approval the envelope is a budget and a record, not a limit you set. What holds the agent then is `rig.toml`, the checks of 4.2, the interlocks and park. Nothing stops a V_coll that the bench allows and the device does not tolerate (1.2, "Limits"). `Close` in the panel and `Abort` still work. To go back, set `false` and restart the service.

## Approving a plan

The `Plans` chip in the bar shows how many plans wait for a decision. Click it to open the plan panel beside the view; it shares that place with the assistant, so opening one closes the other. An agent proposes a plan through the service (`POST /plans`); without automatic approval the panel is the only place a plan is approved.

| Step | What to check |
|---|---|
| Read the goal | It says what will be measured |
| Read the envelope table | The modules, parameters and loops the agent may use (Scope, Parameter, Allowed). Voltages, currents, temperatures, delays and the scan axis are always listed; other values fixed to one setting fold under `more fixed values`, and the approval covers them too. A range wider than the device tolerates is a reason to reject: V_coll and the temperature first (1.2, "Limits") |
| Read the caps | Runs, Time and Approval: the runs and time used of those allowed, and the approval's lifetime |
| Approve | Click `Approve`, then `Approve <fingerprint>?` within 6 s. The approval covers exactly this plan |
| Or reject | `Reject`. The agent sees the decision and may propose another plan |

An approved plan accepts the agent's runs until it is closed, expires, or has used its runs or its time. Closing it in the panel (`Close`) stops further submissions; it does not stop a run in progress.

## While the agent runs

Each run of the agent appears in the run list like any other, with the plan it ran under. Every check, interlock and park applies as for a run an operator starts.

| To | Do |
|---|---|
| Stop a run | The run monitor's `Stop after shot` or `Abort`, or `All off` on the strip (1.3) |
| Stop the plan | `Close` in the plan panel |
| See what the agent asked for | The run's record (results tab) lists its parameters and the plan |

A submission outside the plan is refused before it reaches the bench, with the reasons; the agent has to propose a new plan for it. A service restart forgets every plan, approved or not.

## Connecting an agent

The service offers the Model Context Protocol at `http://127.0.0.1:8900/mcp`, on this PC only. For Claude Code:

```
claude mcp add --transport http bace http://127.0.0.1:8900/mcp
```

The agent then reads the bench, the modules and this manual, proposes plans, and starts and stops runs under them. It has no tool that approves a plan.

## Restarting the service

`Restart` in the bar, twice within 6 s, or `POST /service/restart` over the tunnel, ends the service and starts it again from the files on disk. Use it after a change to the code, `rig.toml` or `run.toml`.

| Point | Behaviour |
|---|---|
| Before it ends | The new code and configuration are tried in a separate process. If they fail, the service keeps running and answers with the error |
| A run in progress | Refused unless `force` is set. The console's button sets it, and aborts the run |
| After | The bench is parked, the session has a new id, and every plan is forgotten. Output goes to `runs\logs\` |
| The tunnel | Stays up; it is a separate process |
