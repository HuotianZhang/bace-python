# Data

Every file the bench writes, where, and what it holds. Measurement files, journals, saved benches and recipes are under the service's `--out` folder, `runs/` by default; the launcher's logs are always under the repository's `runs/logs/`.

## Folders and names

| Path | Written by | Holds |
|---|---|---|
| `runs/<run folder>/` | A `bace` or `jv` module run | One HDF5 file and the `.dat` files of that run |
| `runs/<pipeline name>_<stamp>/` | A pipeline | One folder per module run inside it. The stamp is the time of Start, so a Dry run shows the pattern, not the name |
| `runs/journal/<session>.jsonl` | The service | The session's journal |
| `runs/bench/<name>.json` | Save on the bench tab | Every module's parameters with their layers |
| `runs/recipes/<name>.json` | Save on the pipeline tab | A pipeline tree and the bench it was saved with |
| `runs/logs/service_<stamp>.log` | `BACE.pyw` | The service's output |

A run folder is named from the run's metadata, fields joined by `_`:

    s4_PTQ10IT4F_pxa_290K_1020mVLED_906mVVOC_offsetcorr_20260807_111521

| Field | Source |
|---|---|
| `s4`, `PTQ10IT4F`, `pxa` | `[sample]` sample, material and pixel, reduced to safe characters and at most 24 characters each |
| `290K` | The temperature; how it was obtained is stored in the file, not in the name. It is not typed in the sample panel: a bench with a 331 reads the controller as each node starts, and a typed value could go stale and file a run under the wrong temperature |
| `1020mVLED` | The 33220A LED level, mV |
| `906mVVOC` | The V_oc the axis was centred on, mV |
| `offsetcorr` | Present when the baseline was subtracted |
| a slug of the comment | When `[sample] comment` is set |
| `20260807_111521` | The start of the run |

The name is a convenience; the file holds every field in full (`storage/naming.py`).

## HDF5

A BACE run writes `run<stamp>.h5`, schema `bace-run/3` (`storage/hdf5.py`): the arrays at full precision and the settings that produced them. A J–V run writes `jv<stamp>.h5`, schema `bace-jv/4`, with its settings under `/config/jv` and its curves under `/curves` (`storage/jv.py`). The BACE file:

| Node | Content |
|---|---|
| `/` attributes | `schema`, `software`, `loops_planned`, `loops_completed`, `complete` |
| `/metadata` | The sample block, the temperature with `temperature_how` and `temperature_source`, LED level, V_oc |
| `/config/rig` | `rig.toml` as used |
| `/config/run` | The run settings the scan executed with (`RunConfig`); the axis, the sample, the rig and the read-backs are in the other groups |
| `/config/resolved` | What the instruments reported at setup, such as `:OUTP:POL` |
| `/axis` | `values`, and `vpre`, `vcoll`, `delay_ns` at every point; attributes `name`, `unit`, `voc` |
| `/charge` | `q` (loop, point), `mean` and `std` (point), in C |
| `/traces` | `time`; `light`, `dark`, `photocurrent` (point, sample) averaged over loops, in A; `trace_t0` and `window` per point; `sync_light`, `sync_dark` in V; `monitor_light`, `monitor_dark` in V with `monitor_channel`; `shots` (loop, point, sample) only with `store_shots` |
| `/diagnostics` | Per shot (loop, point): averages counted, spike lag and edges, Sync lag and edges, levels before the trigger, `late_offset_ua`, `dark_first` |
| `/intensity` | `mean`, `std` per point, in W, when the power meter was read |

A partial run is written like a complete one: the rows of loops that never ran are NaN, and `loops_completed` says how many did. Read `loops_completed`, not the array's shape.

`store_shots` keeps every shot's photocurrent: at 51 points × 100 loops × 4000 samples that is 163 MB per run.

`tools/reintegrate.py` reads a file and recomputes Q for another window (2.2).

## Legacy .dat

The `.dat` files are those the LabVIEW program wrote, byte for byte, so existing analysis scripts read them unchanged. `tests/test_storage.py` rewrites a LabVIEW archive through `storage/legacy_dat.py` and compares the bytes.

| File | Content |
|---|---|
| `1_averagesQ<stamp>.dat` | V_pre, V_coll, delay, Q, standard deviation of Q per point |
| `1_allLoopsQ<stamp>.dat` | Q per loop and point |
| `1b_averagesIntensity<stamp>.dat` | Mean and standard deviation of the light power per point, when it was read |
| `2_averagesPhotoCurrent<stamp>.dat` | The loop-averaged photocurrent per point against time, after the baseline when `offset_correct` is set |
| `4_averagesLightCurrent`, `4_averagesDarkCurrent` | The two traces per point against time |

The photocurrent of each shot is in the HDF5 file with `store_shots` (`/traces/shots`); it has no `.dat` file.

Format: ASCII, tab-separated, CRLF line endings, values as `%.5E` with an unpadded exponent, header text with the original spacing. The V_pre column labels of `1_allLoopsQ` are fixed-point. Matrix files have a blank line after the header. Six significant figures: the HDF5 file is the precise record.

A J–V run writes `BACE_JV_Data_<stamp>.dat` and `BACE_JV_Parameters_<stamp>.dat` beside its HDF5 file (`storage/jv.py`); current densities are in mA/cm². These follow the same format but have not been compared with a LabVIEW J–V file.

## The journal

`runs/journal/<session>.jsonl`, one JSON object per line, appended and flushed line by line and never rewritten (`service/journal.py`). A session that ends abnormally leaves every line up to its last event.

| Line | Content |
|---|---|
| First line, `SessionStarted` | Mode, configuration paths, the code fingerprint, the instrument writes made at startup |
| `RunQueued` | Module and tree, the sample block, the folder; for a manual run also the parameters chosen and resolved |
| `RunStateChanged` | Each state transition, ending in a terminal state and then `parked` |
| `StepDone`, `Progress`, `Verdict`, `Notice`, … | The run's events, with arrays reduced (`service/wire.py`) |
| `NeedsOperator`, `OperatorResumed` | A pause and its answer |
| `NodeDone` | A module node's outcome, counts, folder and summary |
| `BenchAction` | An action taken from the console, with the values before it |

Every line is an envelope with `seq`, `ts`, `run_id`, `node_path`, `type` and `data`. The service reads the journal back for the run list, a run of an earlier session, the last-used parameter layer and the settle-time history used by the cost estimate.
