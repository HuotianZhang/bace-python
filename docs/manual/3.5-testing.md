# Testing

What the suite covers, how to run it, and what only the bench can show.

## Running the suite

From the repository root, with the `service` and `dev` extras installed (`pip install -e .[service,dev]`):

```
python -m pytest -q
node --test "ui/tests/*.test.mjs"
```

The first runs every Python test and, through `tests/test_ui.py`, the console's tests when Node is present, except `live.test.mjs`, which needs a running service; the linter runs when ESLint is installed. The second runs the console's tests alone. On the lab PC use `py -3` for `python`.

Every pull request runs the suite on Ubuntu with Python 3.11 and 3.12 and on Windows with Python 3.11 (`.github/workflows/tests.yml`). No test opens an instrument.

| Area | Files |
|---|---|
| Physics and numerics | `test_axis.py`, `test_diagnostics.py`, `test_reintegrate.py`, `test_transient_sim.py`, `test_jv.py`, `test_intensity_series.py` |
| Drivers, against recorded instrument behaviour | `test_drivers.py`, `test_drivers_direct.py`, `test_sync.py`, `test_bench.py`, the console tests |
| Storage | `test_storage.py` |
| Parameters | `test_params.py` |
| Service | `test_service_*.py`: session, worker, pipeline, executor, journal, wire, modules, rigs, temperature, assistant, and the HTTP API end to end |
| Launcher | `test_launcher.py` |
| Layering | `test_architecture.py` (3.1) |
| Real data | `test_regression_20260807.py`, `test_acceptance_20260902.py` (below) |

One test, `test_bench.py::test_dio_backend_explains_itself_when_neither_route_works`, assumes that the DIO library does not load and that no DIO bridge answers. On a machine where either works, such as the lab PC, it fails; the test depends on its environment.

## The simulator

`bace/drivers/simulated.py` implements every Protocol against one simulated bench, so a run, a pipeline and the whole service work without hardware (`python -m bace.service --sim`). The device model is a solar cell with a geometric capacitance, an extraction time constant, a stored charge that grows exponentially with V_pre, and a V_oc that follows the LED level; its numbers are set to give charges of the size the bench measures. The instruments reproduce the behaviour that matters to the code: the inverting amplifier, the sense resistor and `current_sign`, the digitiser's averaging and its range, the shutter, the relay interlock and the 331's settling.

The simulator tests the code paths, not the physics. A result on the simulator says that the software does what it is told; it says nothing about the device.

`--fast` makes every wait through `RunContext.sleep` return at once, so settle times and holds take no time; a pause for the operator still waits for an answer. It is refused without `--sim`.

## The regression run

`bench-archive/` holds one run of the LabVIEW program: its light and dark traces and the photocurrent and Q it computed. `tests/test_regression_20260807.py` recomputes the photocurrent and Q from those traces with `bace.core` and requires agreement within the rounding of the files' six significant figures. It tests the arithmetic: the same traces in give the same charge out.

`acceptance/20260902_service-vs-labview/` holds a run of the service and a run of the LabVIEW program on the same device. `tests/test_acceptance_20260902.py` checks that the service's Q follows from its own stored traces, that both photocurrents agree in sign and shape, and that the file records the validated polarity configuration. It tests the chain, not the absolute charge: the device changed between the two runs.

## On the bench

`python -m bace.bench` checks a real bench in stages (`../bench-checkout.md`). Each stage past the first three is opt-in. A stage that drives the device needs its flag and asks for a typed confirmation, which `--yes` skips.

| Stage | Flag | Does |
|---|---|---|
| offline | always | The package on this machine; no instrument |
| discover | always | Lists VISA resources and asks `*IDN?` at each configured address |
| local | always | The DIO library, the 1918-C and the 331 |
| read | `--read` | Reads back every instrument's settings |
| configure | `--configure` | Sends the configuration commands and reads each error queue; outputs stay off |
| acquire | `--acquire` | One digitiser acquisition; the trigger must be running |
| sync | `--sync` | Where the bias step sits in the LED cycle; digitiser only |
| dio | `--dio` | Walks the four shutter and relay states and measures, with the 2400, the voltage at 0 A and the current at 0 V and +0.5 V in each; the sample stays connected and the LED on |
| outputs | `--outputs` | Turns the outputs on with no sample connected |
| measure | `--measure` | One real transient on a sample |

What the suite cannot test, and only a bench measurement can:

| Property | Measurement |
|---|---|
| The timing constants: `trigger_offset_s`, the light-off time | A delay scan (2.4) |
| The absolute scale: R_s and the digitiser's vertical scale | A capacitor of known C (2.4) |
| The drift between the two traces | A null run (2.3) |
| A complete extraction | Scans of V_coll, delay and window (2.4) |
