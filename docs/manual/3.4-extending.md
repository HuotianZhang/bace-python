# Extending

Where a module, an instrument, a check or an assistant tool is added, and what has to change with it. Each addition comes with tests on the simulator (3.5).

## A module

A module is one kind of measurement or action that a card on the bench tab and a node in a pipeline can run. The catalogue in `bace/service/modules.py` holds them all and serves their specifications and values through `GET /modules`. A card on the bench tab also needs an entry in `ui/lib/fields.js`.

| Step | Where |
|---|---|
| 1 Name it | `MODULE_NAMES` in `service/modules.py`. For a bench card, add it to `BENCH_CARDS`, which sets the order of the cards, and lay out its controls in `LAYOUT`, both in `ui/lib/fields.js` |
| 2 Its parameters | A function returning `ParamSpec`s (`params.py`): name, type, default, unit, limits, group, and a one-sentence `doc` that the console and the assistant show. Register it in `Catalogue.__init__` under `self._params`. |
| 3 Its spec | An entry in `self._specs`: title, kind (`measurement`, `utility`, `observer`), status, the relay position it needs (`dc`, `transient` or none), whether it provides a V_oc, and which parameters are LED levels |
| 4 Its generator | `_build_<name>(self, p, ctx, rig)` returning an iterator of events (`experiment/events.py`). Refuse what can be refused before the generator exists, by raising `ModuleError`. Use `ctx.sleep` for every wait, so an abort and `--fast` reach it, and `ctx.abort` at each natural boundary. |
| 5 Its files | Wrap the generator in a recorder (`storage/`) if it measures. Append the folder to `ctx.folders`. |
| 6 Its run.toml table | If its parameters belong in the recipe, map the keys in `_TOML` in `modules.py`; extend `config.py` when the loader outside the service reads them too |
| 7 Its checks | Add any check the module needs (below) |

`wait` and `note` in `modules.py` are the smallest complete examples; `bace` is the full one.

## An instrument

Each instrument role is a Protocol in `bace/drivers/protocols.py`: `BiasSource`, `Digitizer`, `SourceMeter`, `Shutter`, `PowerMeter`, `LedSource`, `Router`, `TemperatureController`. The measurement code uses the Protocols; the service builds the concrete drivers and reads some of them back through driver-specific methods.

| Step | Where |
|---|---|
| 1 The contract | A Protocol in `protocols.py`, or a method added to an existing one. Units in the names (`_v`, `_s`, `_a`). |
| 2 The real driver | A class in `bace/drivers/` that sends the commands. Read the instrument's error queue after configuration, and implement `read_state()` with queries only, so the bench read-back can call it at any time. |
| 3 The simulated driver | A class in `drivers/simulated.py` that behaves as the instrument does, including its failures, wired into `SimulatedRig` and `make_bench` |
| 4 The rig | A field on `Rig` (`experiment/rig.py`), optional unless every run needs it; extend `Rig.park` if the instrument has an output to switch off |
| 5 The bench | Build it in `service/rigs.py` `Bench.build_real`, report it as unavailable with the reason when it cannot be opened, and read it back in the bench snapshot |
| 6 The addresses | A table or keys in `rig.toml`, loaded in `config.py` |
| 7 The check-out | A stage in `bench/checks.py` that sends its commands with nothing connected (3.5) |

`tests/test_architecture.py` checks Protocol conformance for the main real drivers and the simulated roles; extend it for each added driver. Keep `pyvisa` imports inside functions (`Bench.build_real`, the bench harness's `open_visa`), so the simulator runs without it.

## A check

The pipeline validation runs every check in a fixed order and returns its verdicts at the levels `ok`, `info`, `warn`, `crit` and `invalid` (`service/pipeline.py`). A `crit` or `invalid` verdict refuses the run.

| Step | Where |
|---|---|
| 1 Its id | A dotted string added to `CHECKS`, such as `chain.bias-arm`. The console keys on these strings; never rename one. |
| 2 Its function | `_c_<name>(facts) -> list[Verdict]`, registered in `_CHECKS` in the same order. It reads the tree, the bench snapshot and the history from `_Facts`, and touches no instrument. |
| 3 Its text | The message states the evidence and then the remedy (`../style.md`) |
| 4 Its tests | `tests/test_service_pipeline.py`: the condition that triggers it, and one that does not |

A check on a single shot, rather than on a tree before the run, is a verdict in `service/wire.py`, computed from the diagnostics in `core/diagnostics.py`.

## The assistant's tools

The console's assistant answers with a fixed set of tools (`service/assistant.py` `TOOLS`). Each reads the session and returns text; none changes the bench.

| Step | Where |
|---|---|
| 1 Its schema | An entry in `TOOLS` made with `_tool(name, description, properties, required)` |
| 2 Its answer | A branch in `run_tool` that returns the result as compact JSON or text, within `TOOL_TEXT_LIMIT` |
| 3 A document | A key in `DOCS`, with the path and a one-line description, makes a file readable through `read_doc` |
| 4 Its tests | `tests/test_service_assistant.py`, against the fake provider |

A tool that changes the bench needs an approved experiment plan and is out of scope for the present assistant.
