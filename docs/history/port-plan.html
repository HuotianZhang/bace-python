Every blocker is cleared and the first increment runs. The two programs were parsed straight out of their binary .vi containers without LabVIEW; the duplicated hierarchy then gave up the complete command set of all four instruments.

The decisive find: the measurement physics never lived in G wires. It lives in eight MathScript nodes, which are MATLAB-dialect text. Loop generation, pulse-level mapping, dark subtraction, baseline correction, running averaging and the charge integral are all already source code, and they are now ported and running against synthetic data.

What the G diagram contributes is the plumbing — instrument sequencing, timing, file writing — and that is exactly the part being redesigned rather than transliterated.

The experiment, as the code defines it

The front panel has two buttons, JV and BACE, wired to the two frames of an event structure. They are two separate experiments sharing one panel.

JV — intensity-dependent current–voltage sweep

For each LED drive voltage from Start Voltage LED to End Voltage LED in steps of dV LED: set the 33220A DC offset, wait LED stab. time, then sweep the Keithley from Start Voltage to End Voltage, averaging Averaging readings per point with Stab. time between them. Current is divided by Pixel Area. Voc comes from Threshold 1D Array → Interpolate 1D Array on the current column — a linear interpolation of the zero crossing. Results go to BACE_JV_Data_*.dat and BACE_JV_Parameters_*.dat.

BACE — bias-assisted charge extraction

For each LED drive voltage: measure Voc, Jsc and Jsat on the Keithley, optionally read the Ophir meter, then hand three prebias points to the transient engine and record the extracted charge at each.

A detail worth confirming

The parent VI passes Vpre1 = Voc − dV and Vpre2 = Voc + dV, and the engine expands that to linspace(Vpre1, Vpre2, N) with N = |Vpre1 − Vpre2|/dV + 1 — three points. That is where the Vpre1/2/3 and Q1/2/3 columns in your .dat files come from, and the archived data confirms it: dV = 10 mV, Vpre2 exactly equal to the measured Voc. The evident purpose is dQ/dV around Voc — the differential capacitance needed to strip the geometric-capacitance charge out of Q. Worth confirming that is what you intend it for, because the redesign should make that correction explicit rather than leaving it implied by three adjacent columns.

The recovered maths

These are extracts from the MathScript nodes, unedited. The full set is in D:\BACE\_decompiled\mathscript_algorithms.txt.

Sweep generation

%calc loop parameters
N = abs(Vpre1-Vpre2)/dV + 1;
Vpre1Loop = linspace(Vpre1,Vpre2,N);
Vcoll1Loop = Vpre1Loop*0+Vcoll;
Delay1Loop = Vpre1Loop*0 + Delay;

VpreAllLoops = repmat(Vpre1Loop,1,NLoops);          % all Loops
VpreAllLoops = reshape(VpreAllLoops,1,numel(VpreAllLoops));

Pulse levels — polarity, amplifier, trigger offset

Vpre = VpreAllLoops(i);
if NewSample == 0
  LoLvlL = Vcoll;   HiLvlL = Vpre;                  % light
  LoLvlD = -abs(Vpre - Vcoll);  HiLvlD = 0;         % dark
else                                                % invert & switch
  LoLvlL = -Vpre;   HiLvlL = -Vcoll;
  LoLvlD = 0;       HiLvlD = abs(Vpre - Vcoll);
end
HiLvlL = HiLvlL/PulseAmp;   LoLvlL = LoLvlL/PulseAmp;
HiLvlD = HiLvlD/PulseAmp;   LoLvlD = LoLvlD/PulseAmp;

T = 0e-9;                                           % 47e-9 in the single-step node
Delay = Delay*1e-9 + T;
Width = Width*1e-9;

Two nodes disagreed on T: the single-shot path added a 47 ns offset, the looping path added zero. Corrected 2026-09-02 — zero is the right one. The call made here picked 47 ns, and that was wrong: a scan takes the looping path, and measurement confirms it. At the same Delay(ns) = 90, LabVIEW and the port both put the displacement spike at 328 ns of record time, so :PULS:DEL1 receives delay_ns unchanged. pulses.TRIGGER_OFFSET_S is still the one place it lives; its value is now 0.0.

Charge extraction

PhotoC = LightC - DarkC;
T = dt*(NP-1);  time = 0:dt:T;
if OffCorr == 1
  PhotoC = PhotoC - mean(PhotoC(time > T/10*9));    % baseline: last 10 %
end

% running average across loops
if Loop == 1
  avPhotoC(Step,:) = PhotoC;
else
  avPhotoC(Step,:) = (PhotoC + (Loop-1)*avPhotoC(Step,:))/Loop;
end

% charge integral
allQ(Loop,Step) = sum(PhotoC(time > t0Int))*dt;
for j = 1:NumStepsPerLoop
  QStep   = allQ(~isnan(allQ(:,j)), j);
  meanQ(j)= mean(QStep);   stdQ(j) = std(QStep);
end
Free gift

One MathScript node is a synthetic-data generator — an error-function rise into an exponential decay, plus noise, standing in for a real transient. Porting it gives a hardware-free simulator on day one, so the whole pipeline can be built and tested away from the rig.

The driver layer, recovered

The duplicated hierarchy — 907 VIs — was decompiled the same way as the main programs. Every command string below is the literal format string LabVIEW sent, not a reconstruction from a manual. The full reference is in D:\BACE\_decompiled\instrument_commands.md.

Agilent 81150A

Shape, levels, timing and trigger are all straightforward SCPI on an indexed channel:

:FUNC1 PULS;                      # shape
:VOLT1:HIGH %g;  :VOLT1:LOW %g;   # the mapped prebias / collection levels
:FREQ1 %g;                        # repetition rate
:FUNC1:PULS:WIDT %g;              # width
:PULS:DEL1 %e;                    # delay — where the trigger offset lands
:ARM:SOUR1 EXT;  :ARM:SLOP POS;   # external trigger
:OUTP1 ON;

Infiniium — the acquisition core

# session
:SYST:HEAD OFF; *CLS; *ESE 1; *SRE 32; :WAV:BYT MSBF; :WAV:VIEW MAIN;
# vertical / horizontal
:CHAN%d:OFFS %g;RANG %g;   :CHAN%d:PROB:EXT:GAIN %g;
:TIM:RANG %g;  :TIM:POS %g;  :ACQ:POIN %d;
# averaging — the panel's "# Averages (200)"
:ACQ:AVER ON;  :ACQ:AVER:COUN %d;
# trigger: edge normally, runt for the window mode
:TRIG:MODE EDGE;  :TRIG:EDGE:SOUR %s;  :TRIG:EDGE:SLOP NEG;
:TRIG:MODE RUNT;  :TRIG:RUNT:POL %s;  :TRIG:RUNT:TIME %g;
# readback
:WAV:SOUR %s; :WAV:FORM WORD;
:WAV:POIN?;:WAV:XOR?;:WAV:XINC?;:WAV:YOR?;:WAV:YINC?;:WAV:YREF?;
:WAV:DATA?                        # IEEE block

Scaling comes from the driver's own annotation: volts = (raw − YREF)·YINC + YOR, time = XOR + k·XINC. The BACE path additionally clears waveform memory and hides the function traces before each run: :RUN;:WMEM1:CLE;:FUNC1:DISPLAY OFF;:FUNC2:DISPLAY OFF;. Completion is polled with *OPC then *STB?, not a blocking *OPC?.

Keithley — the Voc/Jsc routine, verbatim

# Jsc: source 0 V, measure current
*RST
:SOUR:FUNC:MODE VOLT; :SOUR:VOLT:LEV 0; :FORM:ELEM CURR; :ROUT:TERM FRON; :OUTP ON
:SENS:FUNC 'CURR:DC'; :SENS:CURR:PROT:LEV <compliance>
:READ?

# Voc: source 0 A, measure voltage
*RST
:SOUR:FUNC:MODE CURR; :SOUR:CURR:LEV 0; :FORM:ELEM VOLT; :ROUT:TERM FRON; :OUTP ON
:SENS:FUNC 'VOLT:DC'; :SENS:CURR:PROT:LEV <compliance>
:READ?

Jsat uses the current-measuring form held at the panel's Vcoll corresponding to Jsat. Sweeps use :SOUR:VOLT:STAR/:STOP with :SOUR:SWE:POIN, and :CURR:NPLC plus :AVER:COUN set the integration and averaging.

Shutter

Deditec USB digital I/O through delib.dll. The LabVIEW Dapi *.vi wrappers are nothing but Call Library Nodes, so ctypes reaches the same entry points:

ULONG DapiOpenModule(ULONG moduleID, ULONG nr);   // -> handle, 0 on failure
void  DapiDOSet1(ULONG handle, ULONG ch, ULONG data);
ULONG DapiCloseModule(ULONG handle);

One shutter, on module ID 9, module number 0, channel 0; 1 opens, 0 closes. BACE_Mehrdad.vi also carries constants for module number 1 — historical, unused. The copy on the rig, D:\BACE\shutter\builds\data\delib.dll, is 32-bit — PE32, machine 0x014C, exporting all four Dapi entry points.

Newport 1918-C — the one genuinely new driver

It is not a VISA instrument. It speaks a proprietary USB protocol through Newport's own usbdll.dll (product ID 0xCEC7, typically a 32-bit build), with entry points newp_usb_open_devices, newp_usb_send_ascii, newp_usb_get_ascii. On top of that sits an ASCII command set:

PM:Lambda <nm>      # set detector wavelength
PM:Power?           # instantaneous power
PM:DS:Clear         # data store: clear, size, interval, enable
PM:DS:SIZE <n>
PM:DS:ENable 1
PM:DS:COUNT?        # poll until full
PM:STAT:MEAN?  PM:STAT:SDEV?

The data-store path is the right one for BACE: it replaces the mean and standard-deviation intensity columns the Ophir fed, in one buffered read rather than a poll loop. Its DLL is almost certainly 32-bit like the shutter's — see below.

The 32-bit problem

Two instruments are reached through vendor DLLs rather than VISA. delib.dll is 32-bit only — verified in both the build output and the installed runtime — and Newport's usbdll.dll ships from a Program Files (x86) install, so almost certainly the same. That looks at first like it forces a 32-bit service.

It does the opposite. SciPy stopped publishing win32 wheels at Python 3.10, so a modern 32-bit Python on Windows cannot install the measurement core at all. A 32-bit service is not on the table.

So the DLLs move into their own process:

64-bit service  --(JSON lines over 127.0.0.1)-->  32-bit helper  --> vendor DLLs
   numpy, scipy                                     delib.dll
   experiment, storage, UI                          usbdll.dll

Both devices are low-rate — a shutter toggle and a buffered power read — so the round trip costs nothing measurable next to instrument settling times. The helper dispatches to an explicit method table (no pickling, no dynamic import) and binds to loopback only. It is built and its transport is tested; BridgedShutter presents exactly the same interface as the direct backend, so the experiment code never learns which one it has.

Settled — there is no 64-bit DELIB

The installed runtime is C:\Windows\SysWOW64\delib.dll, machine 0x014C, with delibJNI.dll beside it; C:\Windows\System32 holds no delib at all. The SDK in D:\BACE\DELIB agrees — its lib\delib.lib is a 32-bit import library and all 73 DllImport attributes in include\delib.cs name "delib.dll", with no delib64 anywhere. Deditec does ship 64-bit builds and marks them with a 64 suffix (the bundled FTDI driver has ftd2xx64.dll), so the absence is real rather than a naming accident. The helper process is permanent.

Three deliberate deviations

  • A latent bug in the point count, fixed. LabVIEW computed N = abs(Vpre1−Vpre2)/dV + 1 and truncated. With Vpre1 = Voc − dV and Vpre2 = Voc + dV, floating-point Voc values push that ratio just under the integer — Voc = 0.720555, dV = 0.01 gives 1.9999999999999, truncating to N = 2 and silently dropping the middle prebias point. Rounding to nearest fixes it. Worth checking whether any archived run lost a column this way.
  • Sample standard deviation. MathScript's std is ddof=1; NumPy defaults to ddof=0. Using the default would have shrunk every error bar.
  • The trigger offset, in one place. As above — and measured to be 0 on 2026-09-02.

The charge integral stays a rectangular sum(...)·dt rather than a trapezoid, so numbers remain comparable with the LabVIEW output. Changing it should be a decision, not a side effect.

Target architecture

Same shape as the JV console and the Lake Shore 331 controller: a Python measurement service holding all instrument state, a browser front end talking to it over WebSocket. One stack across all three programs, one place to fix a driver bug.

Three things the redesign should fix

  • Make the capacitance correction explicit. Three adjacent Q columns that only mean something if you know the convention is a trap. Store Vpre, Q and the derived dQ/dV as named quantities.
  • One canonical output. HDF5 with the full traces, parameters and instrument state per run; the flat .dat files written alongside for continuity with your existing analysis. Right now the raw transients are averaged away before they hit disk.
  • Resolve the 47 ns. One trigger-offset constant, in the config, applied in one place. Done — and the measured value is 0.

Build order

A correction to the earlier plan

Validating the charge integral against the archived data is not possible: the raw transients were never written to disk. Every one of the 1011 .dat files holds aggregated parameters only — LED voltage, Voc, Jsc, Jsat, Vpre, Q and its standard deviation. The light, dark and photocurrent traces were averaged away in memory and discarded. So the archives can confirm the sweep planning and the file format, but the acceptance test for the processing chain has to be a side-by-side run on the rig. It is also the strongest argument for making HDF5 trace storage part of the redesign rather than a later addition.

  1. Maths core done

    Sequence, pulse mapping and processing ported from the MathScript source and running end to end against synthetic transients. Three deviations from the original, each deliberate and documented.

  2. Run loop against the simulator

    Wrap the core in the actual experiment: state machine, per-step light/dark acquisition, live aggregation, storage, and an abort that unwinds the instruments safely. Still no hardware — the simulator stands in for the scope.

  3. Drivers shutter done

    Four PyVISA wrappers from the recovered command set, plus the Newport ctypes wrapper. Each gets a standalone smoke test against its instrument before it goes near an experiment. Settle the 32-bit usbdll.dll question first.

  4. Service and browser UI

    FastAPI plus WebSocket, and the front end: live light/dark/photocurrent traces, Q versus Vpre, progress, and a stop that actually stops. Reuses the patterns from the JV console.

  5. Side-by-side on the rig

    Same sample, same settings, LabVIEW and Python back to back. Agreement on Q(Vpre) within noise is the acceptance test.

Open questions

These are what the driver layer still can't infer for itself.

  • Exact models. Which Infiniium (DSO90xxx? DSOS/MSOS?) and which Keithley (2400 / 2401 / 2440?). The drivers cover the families; a few commands differ between members.
  • Addresses. An NI-MAX configuration export, or just the VISA resource strings. The only one recovered from the diagram is the Ophir's — USB0::0x0BD3::0x0334 — and that instrument is being replaced.
  • The signal path. The panel shows Resistor = 5.192 Ω and Pulse Amp = 4. I read those as the current-sensing resistor and a ×4 voltage amplifier between the 81150 and the device — confirm, and tell me where the probe attenuation of 1.0 sits. Absolute charges depend on this and nothing else in the recovered material pins it down.
  • Two shutter modules. The diagram addresses Deditec module numbers 0 and 1, both on module ID 9, channel 0. Two shutters, or one shutter and something else?
  • Runt-window trigger. There is a panel switch and a dedicated VI. In routine use, or a leftover from the TDCF configuration?
  • Retirement scope. BACE only, or does the TDCF mode come across too? They share almost the whole engine, so doing both is far cheaper than doing them separately later.
