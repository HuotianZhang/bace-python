BACE Port: Current State

Everything verified, everything still inferred, what the audit changed, and what remains to build. Steps 1–8 are done: the full intensity series runs end to end on simulated instruments, writes files your analysis can already read, and every real driver is written against a confirmed address. The rectangular sum was worth keeping

Replacing sum(...)·dt with a trapezoid changes Q by 3.8 × 10⁻⁵ — the fourth significant figure. Small, but 30× larger than the agreement just demonstrated, so it would have shown up as a systematic offset against every historical value. Deliberate beats tidy.

The engine's state machine

A queue-driven handler with ten states, all reachable from the UI event loop. Recovered names and what each does:

StateDoes
InitializeBuilds the UI object, the Experiment object, and registers the file set — 1 text, 8 data, 7 images.

Seven of the eight data-file writes happen after the loop; only 3_allLoopsPhotoCurrent streams. In the port that becomes one event stream with two subscribers — a streaming writer and an end-of-run summary writer — rather than two different call sites.

Where it stands

All 907 VIs of the dependency hierarchy have been decompiled without LabVIEW. Every instrument's command set is recovered verbatim. The measurement core is ported and runs against synthetic data; the shutter and oscilloscope drivers are written from the recovered commands. The architecture is settled: 64-bit Python service, 32-bit helper for the two vendor DLLs, experiment as an async generator emitting typed events.

This audit re-checked every claim. Seven were wrong. They are listed below rather than quietly fixed, because two of them would have produced wrong numbers rather than obvious failures.

What the audit changed

1 · "Blocked" and "unblocked" mean the shutter, not VISA

Read unblocked TDCF.vi takes the light trace; Read blocked.vi takes the dark one. Both are called, in that order. I had read the names as a VISA blocking mode and claimed only one was used. The distinction matters because the two VIs are deliberately asymmetric — see the next item.

2 · Auto-range on the light trace only, never between light and dark

The light read runs scale to maximum and sets the vertical range from the trace it just took. The dark read does not range at all — it inherits that setting. Re-ranging between the pair would change the digitiser scaling and make the subtraction meaningless. A naive port that called the same "acquire" for both would introduce exactly that error, and the result would look plausible.

3 · The scope driver already returns amps

Fetch (Waveform).vi with 50 Ohm? = TRUE divides the scaled voltage by the sense resistor before returning it. My to_current() would have divided by R a second time, scaling every charge by 1/R². Corrected: the driver returns current, and to_current is now documented as being for manually captured voltage traces only.

4 · Timebase is nanoseconds per division, not full screen

The panel value is divided by 1e8 before reaching :TIM:RANG — a ns→s conversion times ten divisions. So Timebase = 200 means 200 ns/div and a 2 µs full screen, with :TIM:POS at four divisions in. I had passed the raw number, which would have given a 200 ns window: ten times too short, and the transient would have run off the screen.

5 · My own extractor was dropping flat-sequence contents

A LabVIEW flatSequence holds its frames under sequenceList, not diagramList. My renderer looked only for the latter, so every flat sequence rendered empty. Fixed and everything regenerated. What was hidden turned out to be mostly Wait (ms) nodes — but the light-trace acquisition was in one of them, which is how finding 1 surfaced.

6 · The "latent truncation bug" is real but rarer than I said

I demonstrated it with Voc = 0.720555, dV = 10 mV — but computing the endpoints as LabVIEW does (Voc ∓ dV, as doubles) that case gives three points, not two. Measured over Voc from 0.5 to 1.1 V at microvolt resolution, the fraction of runs that lose a point is 1.7 % at dV = 20 mV, 0.8 % at 10 mV and 17.1 % at 5 mV. A real hazard, sharply worse at fine dV, and worth a look in the archives if you have ever run at 5 mV. (An earlier version of this page had the 10 mV and 20 mV figures the wrong way round; the rates are now pinned by a test rather than quoted.)

7 · Vpre1/2/3 is a wrapper sweep, not an encoded correction

The wrapper's innermost loop sweeps Vpre_Start → Vpre_End in steps of dV and calls the engine once per step; the three column groups in the parameter file are simply its three iterations. Vcoll1/2/3 and Delay time1/2/3 are the (constant) Vcoll and delay at each of those points, which is why they repeat. So there is no hidden capacitance correction in the file format — the mechanism is plain. Why three points around Voc is still a physics question (Q1 below).

A bug found in my own driver

Reading the wire graph of scale to maximum.vi node by node to write the simulator turned up a mistake in the scope driver I had already written.

The auto-range VI calls Fetch (Waveform).vi with its 50 Ohm? input unwired, so it works in volts. Only Read (Single Waveform).vi wires 50 Ohm? = TRUE with Resistor = 5.192, which is why the engine's arrays are currents. My autorange() was computing the vertical range from the resistor-divided trace — it would have written :CHAN2:RANG a factor of 5.192 too small and clipped every light trace on the first real run.

Fixed: _fetch_volts and _fetch are now separate, and the simulated scope reports clipping so a range that is too small fails a test rather than quietly flattening a peak.

The same reading settled the algorithm itself: Array Max & Min → Subtract → Divide by Scale off. → Multiply by Scale_fac. → Absolute Value → vertical range; and Add → Divide by Scale off. → vertical offset. With the panel's 1.5 and 2, that is range = |1.5·(max−min)|, offset = (max+min)/2, with a 10 mV floor when the peak-to-peak falls below 1 mV.

And it confirmed the light-only ranging from the other side: Read blocked.vi contains the same auto-range call behind a hard-coded FALSE selector, so the dark trace inherits the light trace's range by construction, not by convention.

A free speed-up

That sleep(N/190) is a heuristic, and it sits in addition to the :ADER? polling that already waits for the acquisition properly. At 200 averages it costs about a second per dark trace for nothing. Dropping it and trusting the poll saves roughly five minutes on a 300-point run — the largest single time saving available, and it changes no physics. Worth measuring both ways once on the rig before committing.

Realistic budget per axis point with the sleep retained: ~2 s. A 3-point × 5-loop × 20-intensity run is therefore around 10 minutes of acquisition, plus the DC characterisations. Without the sleep, closer to 5.

Storage: byte-compatible, and verified that way

Your analysis reads the engine's .dat files directly, so the port writes them byte for byte rather than approximately. The test is not that the output looks right — it reads the 7 August archive, writes it straight back out, and compares bytes. All five files match exactly.

Three details a “looks right” writer would have missed:

  1. The exponent is unpadded. LabVIEW writes 9.05000E-1, not 9.05000E-01. Python's %E always pads to two digits, so a naive port differs in nearly every cell.
  2. The format is %10.5e, not %.5e. The field width never shows on a real number — 9.05000E-1 is already ten characters — so it is invisible until a value is not finite. NaN comes out right-aligned as '       NaN'.
  3. The matrix files have a blank second line. Not decoration: a script that skips exactly one header line would read it as a row. Header text is copied verbatim, trailing spaces included, because those are what the parsers on the other side match against.
The archive is a partial run

Which is how the NaN padding surfaced. 100 loops planned, 20 completed, the remaining 80 rows written as NaN, and 1_averagesQ holding the nan-aware mean and sample σ over the 20 — which the ported accumulator reproduces exactly.

So partial runs are the normal case, not an edge case. A fault at loop 7 of 100 must still leave every completed loop on disk. The recorder flushes whatever it has on any exit path, and a test interrupts a five-loop run mid-way and checks the folder is readable, the unrun loops are NaN, and the bias was parked.

HDF5 is the primary store; the flat files are an export. Six significant figures is lossy — visible in that σ comparison, where rounding propagates about a hundred times harder into a spread of 3.6×10−12 than into a mean of 3.7×10−10 — and the flat files carry no record of which instrument was set to what. One .h5 per run holds the arrays at full precision plus the complete rig and run configuration, so a file is sufficient to reconstruct its own run.

Per-shot traces are opt-in. At 51 axis points × 100 loops × 4000 samples that is 163 MB per run — the honest version of Big File?: a choice about disk, made explicitly, rather than a switch nobody remembered.

Two open questions closed from the files

Both looked like they would need a bench answer. Neither did.

New Sample? does exactly one thing — MathScript node 9 swaps and negates the two levels and nothing else:

  LoLvl = Vcoll;   HiLvl = Vpre1;

  LoLvl = -Vpre1;  HiLvl = -Vcoll;

It also sits on scale to maximum.vi's front panel, but that VI's three case selectors are auto scale?, the loop's own shift register, and the peak-to-peak floor comparison — so it is a passthrough there and changes no scaling. Already correctly implemented.

positive jSC? is dead. The label is on the front panel of every version, but the string appears in no block diagram — the only jsc anywhere is the subVI filename measJsc,Voc.vi. It is displayed and saved and never read. Moved to the drop list.

Temperature: deferred, with the seam left open

There is no temperature control anywhere in the 907 VIs — the 290K in the archive folder name was typed by hand. The controller is a Lake Shore 331 at GPIB0::7::INSTR, and it already has its own console with the same shape as this project and an HTTP API on 127.0.0.1:8331. Integration is the step after this one, and the seam is now the same one the power meter uses: ask the console, do not open the instrument. RigConfig.temperature_console exists and is empty; filling it in is the whole integration on this side.

Two cheap consequences taken now. temperature_k is already a metadata field, written into the folder name and the HDF5 metadata, so when the controller arrives it fills itself in and neither the naming nor the stored schema changes. And temperature will not be an Axis — the three axis quantities are per-shot bias conditions set in nanoseconds; temperature settles in minutes. It belongs at the session layer as an outer loop beside the LED level, which is also where the Voc-centring dependency already lives, since Voc moves with temperature exactly as it moves with intensity. The existing layering absorbs it without touching core/axis.py.

The DC and illumination drivers

Written from the recovered command sets, with two deliberate departures from the original — both in the SourceMeter, both about limits.

Compliance is now set before the output is enabled

measJsc,Voc.vi enabled the output and then set the compliance. Between those two commands the SMU sits at whatever *RST left, which is not a limit anyone chose. Reordered, and pinned by a test that asserts the transcript order.

The Voc measurement limits voltage, not current

The recovered routine sets :SENS:CURR:PROT:LEV in both branches, but while sourcing current a current protection does nothing. Sourcing 0 A, the limit that matters is :SENS:VOLT:PROT:LEV — it is what bounds the output if a contact opens mid-measurement.

Everything else is the original's sequence: *RST before each of the three quantities, Jsc then Voc then Jsat, separate settle times for each (three separate panel controls, because a slow cell settles far more slowly at Voc than at Jsc), and the output off again after each — which matters, because the router reads output_enabled before it will move the relay.

The 33220A driver sends the inline strings verbatim and unindexed — that absence of a channel index is how it was told apart from the 81150A in the first place. identify() now refuses an 81150A explicitly, because swapping the two addresses would drive the LED with the collection-field waveform.

The Newport 1918-C goes through the 32-bit bridge and uses the meter's own data store, so a statistic costs one round trip rather than N. It raises rather than returning a mean over however many samples happened to arrive — a silently short average is the kind of error that survives into a published number.

The instruments are not reachable from here, so what these tests pin is what is sent and in what order. That is not a substitute for a bench smoke test; it is what makes the smoke test short, because by then the only unknown left is whether the instrument agrees.

Two config files, written

rig.toml is the bench — addresses, sense resistor, amplifier gain, module numbers. run.toml is the measurement, copied verbatim into the output so a result carries its own recipe. They fail differently, which is why they are separate: a stale rig.toml silently rescales every charge, while a stale run.toml merely repeats a measurement you did not mean to repeat.

The loader refuses unknown keys rather than falling back to defaults. A typo in sense_resistor_ohm that quietly defaulted would produce data wrong by a factor of five with no symptom, and the point of a config file is that someone can read what the run actually used. It also refuses a rig.toml that puts the shutter and the relay on the same DIO module.

J–V is its own module now

It runs with or without BACE, and needs only the SourceMeter — the LED and the relay are used when present, and their absence just means “the illumination is whatever it is” and “nothing is contending for the device”. When a router exists the sweep happens inside router.dc(), so the interlock still applies.

Three things it does that the original did not:

  • Dark and light in one run. The original swept the Keithley under whatever the 33220A happened to be doing. Here a dark scan switches the LED output off rather than setting it low — a sub-threshold level is right for the transient, where the generator must keep producing a waveform, but for a dark J–V there is nothing to keep and an output that is off cannot leak. Both land in the same file set, because a dark curve is only interpretable beside the light curve it belongs to.
  • Both sweep directions, optionally. Curves that differ forward and reverse are hysteresis, which for many chemistries is the most interesting thing in the measurement and is invisible if you only sweep one way. Off by default: it doubles the run and makes “the” curve ambiguous.
  • Derived numbers refuse to be meaningless. A dark curve reports no Voc at all. It still crosses zero — on noise, or on the shunt — and calling that a Voc invents a plausible number from nothing. Current density is omitted rather than defaulted to 1 cm², because defaulting the area silently mislabels A as A/cm².
The simulator cannot disagree with itself

The simulated device now carries a single-diode model whose saturation current is derived from the same Voc the transient axis centres on: I0 = Jsc,ref·exp(−Voc,ref/nkT). So a simulated J–V Voc and a simulated BACE Voc cannot describe different devices, and a test asserts they agree.

Storage writes BACE_JV_Data_*.dat and BACE_JV_Parameters_*.dat in the house format with the recovered column names, plus an HDF5 keeping every curve of a run in one file. Not byte-verified — unlike the BACE writer, no J–V output folder has been read, so this one is a reconstruction. One sample pair would settle it.

Compliance: adjustable, under a ceiling

current_compliance_a moved out of rig.toml into run.toml, because the right compliance depends on the pixel rather than on the bench.

What stayed in rig.toml is a ceiling no run file may exceed. A 2400 will happily push 1 A into a small cell, and a typo in a measurement recipe is a far more likely route to that than a deliberate decision. The loader refuses the run rather than clamping it, so anyone who wants more has to raise the ceiling on purpose.

Correction: the power meter needs no bridge, and no second driver

Reading the existing 1918-C project changed this driver completely, and two of its findings overturn what these pages previously said.

The meter is not 32-bit-only

Newport's package installs both 32- and 64-bit usbdll.dll; the build matching the interpreter just has to be picked deliberately. Only delib.dll — the shutter and relay — is genuinely 32-bit-only, so the helper process carries one target, not two.

Only one process can hold the USB device

And on this rig that process is the 1918-C console. A second driver opening it fails in the confusing way: a bare “no Newport device found” that looks like a cable fault. So the driver here contains no transport code — it is an HTTP client to the console's localhost API, with a direct backend that imports the tested driver for when nothing else holds the meter.

Facts from that project that my first attempt had wrong: the meter echoes the command back before its reply; the terminator is \r, not \r\n; PM:DS:INT is in milliseconds on this firmware, not the 0.1 ms a widely-copied driver claims; PM:DS:BUFFER 0 is needed or the store wraps into a rolling window; and PM:PWS? carries a saturation/overrange status that PM:P? does not. A clipped intensity reading biases every normalisation and looks entirely reasonable, so the status is read and surfaced — but a bad sample is reported rather than raised, because one saturated reading should not abort an hour of transients.

The wrapper, and the interlock proved rather than described

For each LED level: measure Voc, Jsc and Jsat on the SourceMeter under steady illumination, switch the LED to pulsed mode at the same level, and run a transient scan whose prebias axis is centred on the Voc just measured. That last dependency is the whole reason this layer exists — Voc moves with illumination, so the axis cannot be built until the light is on and the SourceMeter has read it.

This is the only place a software mistake reaches the sample, so three things are guarded rather than documented.

The relay test does not just check that nothing raised

It wraps the router and records the state of both sources at the instant each move is requested, then asserts both were quiet. An interlock that is never exercised is an interlock nobody knows works.

The coupling invariant is fed the level the program actually measured at, not the level it intended to. A test runs two illumination points whose Voc differ by more than 20 mV and asserts each axis is centred on its own — a stale Voc could not pass.

Preflight checks everything checkable before the first instrument is touched: no router, no SourceMeter, a “sub-threshold” low level that is not sub-threshold, and the one that would otherwise look like a normal run — an axis centred on Voc with the DC measurement switched off, which would centre on nothing. A series is hours long; finding that at step 40 is the expensive way to learn it.

Unwinding runs on completion, abort, exception and walk-away, in that order of priority: the sources come down first, because the interlock will refuse to act while one is live. Four tests exercise those four exits and assert bias, SourceMeter, shutter and LED are all off afterwards.

Uncalibrated columns are NaN, not guesses

Jsc and Jsat in mA/cm² need the pixel area; the intensity column needs the factor converting meter watts to irradiance at the sample. The original had a Factor control whose value is not in the binaries. A number that looks calibrated and is not is worse than a gap.

Two writers are reconstructions, not verifications: the J–V files and this series summary. The BACE per-run writer is byte-verified against a real archive; these two have no sample to check against. One of each would pin them.

The bench harness

Every SCPI string in this port was recovered from a binary and has never been sent to an instrument. So the harness sends each one and reads the error queue immediately afterwards — that is the whole design, and it turns “does my SCPI work” from a guess into a table of exactly which commands were rejected and what the instrument said about them.

RecordingResource wraps a pyvisa resource and presents the same interface, so the real drivers are pointed at it unmodified. The transcript is of the code that will actually run, not of a test double.

Four defects in my own code, one of them serious.

1 · The report's headline section was wrong

The fetch came back empty — and my explanation was wrong

:WAV:DATA? returned an empty array while the preamble promised 4000 points, with nothing in the instrument's error queue.

The obvious diagnosis was false

I said :WAV:STR ON produces an indefinite #0 block that pyvisa cannot parse. It parses it fine — checked directly against from_ieee_block in pyvisa 1.16.2. The cause is still unknown.

So the driver stopped depending on the diagnosis. _read_waveform takes pyvisa's answer when it is the length the preamble promised, and otherwise reads the bytes itself and parses the IEEE block by hand — both definite and indefinite headers. last_fetch_method records which route was used, so the report says whether the fallback was needed.

Alongside that, three changes that are right regardless:

  1. :WAV:STR OFF. The LabVIEW driver set streaming ON and I copied it. Streaming is for records too large for a definite-length block header (>999,999,999 bytes); a 4000-point WORD record is 8000 bytes. A definite header also lets the reader notice a short transfer, which an indefinite one cannot.
  2. :STOP before fetching. Both autorange and acquire read the channel while the scope was still running. The average is only complete once acquisition has ended anyway.
  3. The driver now says what went wrong. An empty block, or one shorter than its preamble declares, raises an error naming the two things to check rather than failing inside numpy.

And a raw waveform transfer check now reads :WAV:DATA? byte by byte and reports the block header, the declared payload length and the actual one — so if it is still empty, the next report distinguishes an indefinite block from a truncated transfer from something else, instead of prompting another guess.

The :ADER? latch

The acquire transcript showed :ADER? answering +1 about a millisecond after :RUN. The Acquisition Done Event Register is a latch, cleared on read: one left set by a previous acquisition returns immediately and the wait ends before anything has been captured. With 200 hardware averages that means fetching a partial average and never knowing — no error, no symptom, a quietly noisier trace. It is now read and discarded before every :RUN.

A question about the trigger sweep

The recovered driver sets :TRIG:SWE AUTO, which sweeps even when no trigger arrives. If the 81150A sync came loose, every trace would be untriggered noise, the dark subtraction would cancel it, and Q would come out near zero — a plausible-looking result produced by a disconnected cable. TRIG waits instead, turning that into a timeout.

That is a change to acquisition behaviour rather than a bug fix, so it is exposed as a run setting and left at the original's AUTO. Worth switching once the trigger path is known good.

The auto-range was clipping — and the peak was 26 % larger than reported

The one real defect this acquisition exposed, and the reason the first run's headline number was wrong.

Max and min taken from a clipped trace are lower bounds, so a range computed from one is too small — and a single pass cannot escape that. scale to maximum.vi wraps its ranging in a FOR loop, which I had flattened to one pass when porting it.

The measurement the clipped run reported was 26 % low

Peak current from the clipped window: 19.3 mA. Peak current once the window holds the signal: 24.4 mA. A clipped trace does not look broken — it looks like a slightly smaller transient, and every extracted charge downstream of it is quietly an underestimate. This is the class of bug that produces publishable-looking numbers that are wrong, which is why the driver now reports autorange passes, the window sequence it tried, and a warning if it ever gives up while still clipping.

Then: two passes instead of four — confirmed on the rig

Converging is right; taking four acquisitions to do it is waste. The original applies its formula on every pass, clipped or not — but a clipped trace carries no information about how far past the rail the signal went, only that it went. So while clipped, autorange now ignores the reported max and min and grows the window geometrically (×1.8), anchored on whichever edge did not clip so the new span is spent on the side the signal actually ran off. The formula is applied once, to the first acquisition that fits.

A deliberate deviation from the original, and the first one in the acquisition path that changes timing rather than correctness. At ~150 ms per acquisition and 300 steps a run, two saved passes is about three minutes. It also stops as soon as the instrument refuses a wider window — at its own ceiling, another pass would clip identically and cost 150 ms to learn nothing.

And report 8 caught a regression I had introduced four minutes earlier

Along with the growth I had added a readback — report what the instrument took, not what it was asked for — sound reasoning for a scope that quantises its ranges. This one does not quantise; it rounds its reply to three significant figures. Asked for 0.191561 V it answers 1.91E-01, and the readback was quietly throwing away precision rather than gaining it. Worse, the ceiling test compared the reply to the request for equality, so a request for 1.5746 V coming back as 1.57 would have read as the scope refusing to go wider and abandoned a signal that needed more range.

Both are fixed: the reply wins only when it disagrees by more than 2 % (a quantised step is at least 25 % away, display rounding at most 0.5 %), and the ceiling test now asks whether the range grew, not whether it matched. Neither would have shown up in simulation — a fake instrument echoes back what you send it.

Three times per autorange, and Read unblocked TDCF.vi re-ranges on every step. Removing the readback was the obvious move and it was wrong — a test with a scope capped at 0.10 V showed the driver then testing the trace against a window the instrument did not have, and calling a clipped trace clean. The fix is not to read less but to write less: if the computed range is within 2 % of what is already in force, leave the channel alone — no write, no settling query. After the first step of a run that is every step. It is also better physics: the light and dark traces of a step must share a quantisation, which is why the dark trace inherits the light trace's range, and holding the range still across steps extends that to the whole run rather than averaging a hundred loops taken on a hundred slightly different scales.

Where the code actually runs — and a claim I withdrew

Withdrawn: “one store, not two”

The bench reports say Q:\Huotian\bace-python; I had been committing to D:\BACE\bace-python. Report 8 ran 62 seconds after a commit and contained the field that commit introduced, so I concluded the two paths were one store over the network and said so with more confidence than a timing coincidence can carry.

They are not. When Q:\Huotian\bace-python was connected directly, it was ten files behind — it had stopped tracking at 22:50 while D: went on for another hour. Reports 8 and 9 really did run code committed minutes earlier, so something propagates; it is not reliable and I do not know the mechanism. Both copies were made identical at that point (fingerprint d32791817f17; as of 2026-09-02 it is d7daadac0cc1), his 42 bench reports on the Q: side untouched, and every commit is mirrored explicitly rather than assumed.

So every report now carries a code fingerprint — a hash over every .py in the package, path and content — beside the package path and the newest source file. Two reports with the same fingerprint ran the same code; two that disagree about a result while sharing one disagree about the rig. That is a one-line check instead of the hour this cost.

The regression was not running where it mattered. Every report through 8 skipped the archive regression and the byte round-trip, because D:\DATA\TDCF-BACE\data is a sternwarte path and the harness runs on Keplerplatz. Those two are the strongest checks in the suite — 0.6 ulp against a real 2026-08-07 run, and legacy files reproduced byte for byte — and they were proving my copy of the code, not the deployed one. A 540 kB copy of that run now ships in bench-archive/ and --archive defaults to it; report 9 is the first to carry both, and both pass.

Then the question stopped mattering: delib64.dll is installed

Deditec ships DELIB under two names, and I had only ever looked for one:

BuildFileInstalled into
32-bitdelib.dllC:\Windows\SysWOW64
64-bitdelib64.dllC:\Windows\System32

So the helper, the second interpreter and the whole bridge are unnecessary — --dio now loads in-process. Nothing hard-codes a name any more: drivers/delib.py looks at what is present, reads each candidate's PE header, and picks the build matching the interpreter, falling back to the bare name so Windows can search its own path. dll_path under [dio] in rig.toml overrides it.

Deditec's own header confirms nothing else changes. The x64 build is declared extern "C" _declspec(dllexport), so the exported names are undecorated, and every argument and the module handle stay ULONG — 32 bits in both builds, since Windows keeps long at 32 bits on x64. The c_ulong argtypes were already right; only the filename was wrong.

The one stage with no interlock was the one that moves the relay

Module 1 is the relay that puts the device on either the ×4 amplifier or the Keithley — the single place in this system where a software mistake costs hardware rather than a dataset. routing.Relay has always refused to move it while either source is driving. But --dio drives the DIO line directly, bypassing that class entirely, so it was the way around the interlock — and it was about to be run for the first time with both generator outputs enabled.

It now reads :OUTP1? from the 81150A and :OUTP? from the Keithley and refuses to move anything while either answers 1. An instrument it cannot reach counts as driving: a timed-out GPIB session is not proof that the generator is off.

Before that: the 32-bit Python question, and why the advice was wrong

I told you to start the DIO helper with py -3.11-32. That was a guess dressed as an instruction — nobody had ever started the helper, and the warning I quoted came from a file-bitness scan that never touched it. The check now finds out instead, running each interpreter the launcher knows about to read its real pointer size. Report 9's answer:

32-bit Python : none found
py --list     : -V:3.14[-64] *   C:\Users\PwM\AppData\Local\Python\pythoncore-3.14-64\python.exe

One interpreter, 64-bit. That left two routes — a 32-bit Python, or a newer DELIB — and the second turned out to be the right one. I had also concluded there was “no 64-bit DELIB to point at” because the copy in D:\BACE\DELIB is 32-bit throughout; what I missed is that the 64-bit build ships under a different filename, so the absence of a 64-bit delib.dll proved nothing. The printed helper command now also carries --delib, without which the helper starts with no shutter target at all and every call fails anyway — it remains the fallback for a machine with only the 32-bit library.

And a correction: this does not gate --measure, as I said earlier. That runs today with --manual-shutter, blocking the beam by hand. What the DIO gates is unattended running and the relay that moves the device between the ×4 amplifier and the Keithley.

Open questions

  1. Why three prebias points rather than three repeats at Voc? The mechanism is settled; the intent is not. With the axis now a parameter this is a choice in run.toml rather than a constraint, but it decides what the default should be.
  2. trigger_sweep: AUTO or TRIG? The original leaves the scope in AUTO, and the rig still reads :TRIG:SWE? = AUTO. AUTO free-runs when no trigger arrives, so a dead sync gives you a flat trace rather than a timeout — a silent zero instead of an error. TRIG would fail loudly. The port keeps AUTO as the default to match the original; worth deciding deliberately before the first real run.
  3. The intensity calibration Factor — recovered as a panel constant, its provenance unknown. It scales logged intensity and nothing else.
  4. What the 81150A was doing at 1.263 V / 60 ns / 500 Hz when the first bench session found it. I overwrote those settings during the forced configure and told you at the time; if they were a deliberate setup, they are recorded in report 1 and can be put back.
