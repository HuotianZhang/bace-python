一 · 时间轴

五个信号，一个零点

全部以示波器看到的时间为准，零点取 81150A 的 Sync——也就是正式测量时示波器的触发源。:PULS:DEL1 只延迟输出，不延迟 Sync：把它调到 0，红蓝两条边沿重合。

四 · 推导

那个 47 ns 常数不是线缆延迟

真实的「光灭之后多久开始抽取」是

τ = (:PULS:DEL1 + t_bias) − 122

    :PULS:DEL1 = τ + delay_zero
    delay_zero = 122 − t_bias = 60…75 ns

delay_zero 就是代码里 trigger_offset_s 扮演的角色——但名字、定义和数值都不对。

要改

TRIGGER_OFFSET_S 的含义是错的，值也是错的

core/pulses.py — 现在
TRIGGER_OFFSET_S = 47e-9
"""Fixed delay between the generator trigger and the field arriving at
the device — cable plus instrument latency."""

delay_s = delay_ns * 1e-9 + TRIGGER_OFFSET_S     # → :PULS:DEL1

它不是线缆延迟，而是 delay 轴的零点标定：让 delay_ns = 0 真的等于「场恰好在光灭时到达器件」。

而且它是大数的残差。122 本身 = 502 − 380，两个四五百纳秒量的差。光纤长度、LED 放大器、偏压线缆任何一项改动，这个「小常数」的变化都可能是它自身的数倍。写成 cable plus instrument latency 会让后来的人以为它不会动。

当前 run.toml 的 delay_ns = 88 给出 :PULS:DEL1 = 135，比匹配值高 60–75 ns——标称的「88 ns」实际是光灭后约 150–160 ns。

五 · 落到代码

接线属性进 rig.toml，不进配方

跟 current_sign 同一类：会随台面改动而变的物理常数不能只活在注释里，而且每组数据必须自带它是在哪套时序下测的。

rig.toml
[timing]
led_path_delay_s     = 5.02e-7   # 驱动放大器 + 85 m 光纤。实测
bias_response_s      = 5.5e-8    # 81150A 输出 → 器件响应，47–62 ns
arm_latency_s        = 3.80e-7   # 33220A 驱动沿 → 81150A Sync
delay_zero_offset_s  = 6.7e-8    # 派生：光灭(+122) − bias_response
  • :PULS:DEL1 = delay_ns + delay_zero_offset_s，把 TRIGGER_OFFSET_S 从 core/pulses.py 移走——它是台面属性，不是脉冲计算的一部分。
  • 四个数和派生的零点全部写进输出元数据（HDF5 + .dat 表头），这样一组数据看得出它假设了什么时序。
  • --sync 已经在报告 :PULS:DEL1?；再加一条：把实测的 Sync→输出、驱动→Sync 和配置里的值对照，不一致就 warn。

六 · 复核

delay 扫描是更强的标定

上面的零点是 122 − t_bias，依赖对「光电荷响应在哪」的判读，带 ±15 ns。

Q(delay) 扫描不需要知道 t_bias。曲线的拐点直接就是「场恰好在光灭时到达」的那个设定值——一次测量给出整个偏移，而且用的是最终要用的那个量（电荷），不是中间信号。

扫之前必须先做削顶上报（待改清单第一批已完成）：信号最大的那几个 delay 点最容易削顶，压平的恰好是拐点区域，会给出一个看起来像物理饱和的平台。

实测于 2026-09-01，示波器 DSO9054H。零点 = 81150A Sync = 正式测量时的示波器触发源。
t_led 由放在器件位置的快速 Si 探测器测得；t_bias 由亮暗曲线相减判读，带 ±15 ns。
