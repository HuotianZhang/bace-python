The BACE trigger chain in time

Light takes 502 ns to travel from the 33220A’s drive edge to the sample, 419 ns of it in 85 m of fibre. The code represents that whole chain with a single 47 ns constant — and the part that constant really plays is calibrating the zero of the delay axis.

The delay scan section six asks for was done, and its conclusion supports this page: TRIGGER_OFFSET_S is now 0. At the same Delay(ns) = 90, LabVIEW and the Python port both put the displacement spike at 328 ns of record time — on the scan path, :PULS:DEL1 receives delay_ns itself with no offset at all. So section four’s judgement stands (47 ns is neither a cable delay nor the right number), except that the final answer is not 60–75 ns but 0. The [timing] block of section five is still unimplemented. The full comparison is in docs/history/HANDOVER-2026-09-02.md.

one · the time axis

Five signals, one zero

Everything is in the time the scope sees, with the zero at the 81150A’s Sync — which is the scope’s trigger source during a real measurement. :PULS:DEL1 delays the output only, never the Sync: set it to 0 and the red and blue edges coincide.

four · the derivation

That 47 ns constant is not a cable delay

The real “how long after the light goes out does extraction begin” is

τ = (:PULS:DEL1 + t_bias) − 122

    :PULS:DEL1 = τ + delay_zero
    delay_zero = 122 − t_bias = 60…75 ns

delay_zero is the part trigger_offset_s plays in the code — but its name, its definition and its value are all wrong.

to change

TRIGGER_OFFSET_S means the wrong thing, and its value is wrong too

core/pulses.py — as it stands
TRIGGER_OFFSET_S = 47e-9
"""Fixed delay between the generator trigger and the field arriving at
the device — cable plus instrument latency."""

delay_s = delay_ns * 1e-9 + TRIGGER_OFFSET_S     # → :PULS:DEL1

It is not a cable delay but the calibration of the delay axis’ zero: it makes delay_ns = 0 genuinely mean “the field arrives at the device exactly as the light goes out”.

And it is the residual of large numbers. 122 itself = 502 − 380, the difference of two quantities of four or five hundred nanoseconds. Change the fibre length, the LED amplifier or the bias cable and this “small constant” can move by several times its own size. Writing it as cable plus instrument latency leaves whoever comes next thinking it never moves.

The present delay_ns = 88 in run.toml gives :PULS:DEL1 = 135, 60–75 ns above the matching value — so a nominal “88 ns” is really about 150–160 ns after the light goes out.

five · into the code

Wiring properties go in rig.toml, not in a recipe

The same class as current_sign: a physical constant that moves when the bench is rebuilt cannot live only in a comment, and every set of data has to carry which timing it was measured under.

rig.toml
[timing]
led_path_delay_s     = 5.02e-7   # drive amplifier + 85 m fibre. measured
bias_response_s      = 5.5e-8    # 81150A output -> device response, 47-62 ns
arm_latency_s        = 3.80e-7   # 33220A drive edge -> 81150A Sync
delay_zero_offset_s  = 6.7e-8    # derived: light out (+122) - bias_response
  • :PULS:DEL1 = delay_ns + delay_zero_offset_s, moving TRIGGER_OFFSET_S out of core/pulses.py — it is a property of the bench, not part of the pulse arithmetic.
  • All four numbers and the derived zero go into the output metadata (HDF5 and the .dat header), so a set of data shows what timing it assumed.
  • --sync already reports :PULS:DEL1?; add one thing more — compare the measured Sync→output and drive→Sync against the configured values, and warn where they disagree.

six · the check

A delay scan is the stronger calibration

The zero above is 122 − t_bias, which depends on reading where the photocharge response is, and carries ±15 ns.

A Q(delay) scan needs no knowledge of t_bias. The knee of the curve is directly the setting at which the field arrives exactly as the light goes out — one measurement gives the whole offset, and it does so in the quantity that is finally wanted (charge) rather than an intermediate signal.

Clipping has to be reported before scanning (done, in the first batch of the fix list): the delay points with the largest signal clip most easily, and what gets flattened is exactly the knee region, giving a plateau that looks like physical saturation.
